## tensorflow smoke test — FAIL, real finding not a bug

```
NotFoundError: TPUs not found in the cluster. Failed in initialization:
No OpKernel was registered to support Op 'ConfigureDistributedTPU' ...
Registered devices: [CPU]
```

Root cause, confirmed not an environment misconfiguration:
- `libtpu.so` is present exactly where `TPU_LIBRARY_PATH` points
  (`/usr/local/lib/python3.13/dist-packages/libtpu/libtpu.so`).
- `TPU_ML_PLATFORM_VERSION=2.21.0` matches the installed `tensorflow==2.21.0`
  exactly — not a version mismatch.
- `jax` and `torch_xla` both use the same `libtpu.so` successfully on this
  same runtime, in the same process space.
- The plain PyPI `tensorflow` wheel simply doesn't compile in the
  `ConfigureDistributedTPU` op kernel anymore — TPU support isn't in the
  generic pip package the way it is baked into Kaggle's TPU VM base image
  (per `README.md`'s framework matrix, which assumed pip tensorflow has
  native TPU support — true on Kaggle's preinstalled image, **not
  reproduced here from a plain pip install**).
- Tried `TPUClusterResolver()` (needs a name, this isn't a classic
  Colab TPU-node runtime) and `TPUClusterResolver(tpu="local")`
  (TPU-VM-style resolver) — same missing-kernel error both ways, so this
  isn't a resolver-argument problem either.

Not pursued further this run (needs either a TPU-specific TF build/package
or GCP TPU VM's own preinstalled TF, neither available by plain `pip
install tensorflow` on Colab) — tracked as a new, more specific gap than
SCOPE.md previously had.

## Whisper transcription (`examples/torch_xla/whisper_tpu.py`) — PASS, after one real fix

`openai/whisper-base`, same session, same `xla:0` device.

First call (no extra args) crashed inside `transformers`' own
`_retrieve_segment`: `RuntimeError: Value out of range (expected to be in
range of [-1, 0], but got -2)`. Root cause: the 2s synthetic sine-tone test
input (not real speech) decoded to a 1-token sequence; eager PyTorch
silently clamps `tensor[-2:]` on a length-1 tensor, `torch_xla`'s compiled
slicing throws instead. Real divergence, not a bug in this repo's code —
full writeup in `research/prior_art.md` §7.

Fix: `model.generate(input_features, min_new_tokens=5)` forces a longer
sequence, avoiding the degenerate case.

```
transcribe time: 253.74s   (first-call XLA compile cost, dominates)
text: 'you you you you you'   (garbage — synthetic tone, not real speech,
                                 expected and not a correctness signal)
```

253.74s is a real, quantified cost of the exact problem SCOPE row B1
(growing KV cache forces a recompile every autoregressive step) describes.
Not yet compared against a `StaticKVCache`-based fixed-buffer generation
loop in this repo — that A/B comparison is the natural next step, not done
this session.

## Splash Attention (Category A2-A4) — attempted, blocked, not our bug

Tried `jax.experimental.pallas.ops.tpu.splash_attention` on this same
session (`jax==0.7.2`, `jaxlib==0.7.2`, `libtpu==0.0.21.1`). API confirmed
correct via introspection and matches the module's own reference impl
signature. Execution failed:

```
XlaRuntimeError: INTERNAL: Failed to deserialize the Mosaic module:
INTERNAL: Unsupported version: expected <= 7 but got 8
```

A version-skew bug between this JAX build's Pallas compiler (emits IR
version 8) and the installed `libtpu` (deserializes `<= 7` only) — not a
bug in Splash Attention's API or in how it was called. Didn't attempt to
fix by changing `libtpu` mid-session, since torch_xla/jax/Whisper/
profiling verification above all depend on the exact `libtpu` already
proven working. Full writeup: `research/prior_art.md` §8.
